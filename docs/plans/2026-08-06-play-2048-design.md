# 2048 休息小遊戲 — 設計

2026-08-06

在站內加一個 2048，讓每個人各玩各的，棋盤與最高分存在 Durable Object
裡，換裝置接得回來，另附一份全員最高分榜單。

原版是 [gabrielecirulli/2048](https://github.com/gabrielecirulli/2048)，MIT
授權。

## 定位

**純休息用。** 跟題庫完全解耦 —— 不換步數、不跳題、不影響任何學習指標。
讀書累了按一下，如此而已。入口低調（個人頁一個小連結），不進導覽列。

這個定位是刻意的。把遊戲跟刷題綁在一起（答對才能玩、合成到 512 跳一題）
聽起來有趣，但那會讓一個五百行的休息功能長出對 `attempts`、`drill`、
計分邏輯的依賴，往後每次動學習相關的程式都要多想它一次。休息就讓它只是
休息。

## 架構

三層，彼此不知道對方存在。

### ① 遊戲引擎（純函式）— `frontend/src/lib/game2048.ts`

沒有 React、沒有 fetch、不直接呼叫 `Math.random()`。對外只有：

```ts
type Board = (number | null)[];        // 長度 16 的扁平陣列
type Dir = 'up' | 'down' | 'left' | 'right';
type GameState = { board: Board; score: number; won: boolean; over: boolean };

newGame(rng: () => number): GameState
move(state: GameState, dir: Dir, rng: () => number): GameState
isGameOver(state: GameState): boolean
```

`rng` 由呼叫端注入 —— 正常玩傳 `Math.random`，測試傳固定序列。這樣「新磚
落在哪一格」在測試裡是可決定的，合併規則才驗得動。

`GameState` 直接可 JSON 序列化，也就是直接可以塞進 DO，中間不需要任何
轉換層。

移動合併的規則照原版移植，不重寫。其中一條特別容易寫錯：**同一次移動中
已經合併過的磚，不能再參與第二次合併** —— `[2, 2, 4, null]` 左移的結果是
`[4, 4, null, null]`，不是 `[8, null, null, null]`。

### ② 頁面 — `frontend/src/routes/Play.tsx`

`useReducer` 持有 `GameState`。鍵盤方向鍵與觸控滑動都收斂到同一個
`dispatch({ type: 'move', dir })`。

每次 state 變動後起一個 ~1 秒的 debounce，把整份 `GameState`
`PUT /api/play/state`。`beforeunload` 與 `visibilitychange → hidden` 時強制
flush —— 手機切到背景是最常見的離開方式，只靠 debounce 會掉最後幾步。

### ③ 持久層 — `worker/play-2048.ts` + `worker/routes/play.ts`

`Play2048` 是 SQLite-backed DO（`new_sqlite_classes`，免費方案可用），
單一 instance（`idFromName('main')`），沿用 `UserState` / `ChatRoom` 的
既有模式。路由掛 `app.route('/api/play', playRoutes)`。

`c.var.email` 由既有的 Access middleware 提供，DO 永遠不會收到未驗證的
呼叫，所以 DO 內部不做任何權限判斷。

### 資料流是單向的

引擎算出新 state → React 畫 → debounce 推 DO。**DO 從不回推。** 只有頁面
掛載時 `GET` 一次當初始值。

沒有 WebSocket、沒有即時同步，因為同一個人不會同時在兩台裝置上玩同一局。
真的發生了，最後 flush 的那台贏 —— 這對休息遊戲是可以接受的結果。

## 為什麼開新的 DO class，不沿用 `UserState`

`UserState` 已經是「單一 main instance、依 email 分列的 per-user 狀態」，
2048 棋盤概念上完全吻合，加一張表就好。

但 DO 是單執行緒的。遊戲是每步 debounce 寫入（秒級），`UserState` 是換頁
才寫一次（分鐘級）。塞進同一個 instance，等於讓某人玩遊戲時，其他人的
「上次停在哪」讀取要排在遊戲寫入後面。

隔離的成本只有一個檔案、一個 binding、一個 `[[migrations]] tag = "v3"`。
很便宜，就分開。

## DO schema

```sql
CREATE TABLE IF NOT EXISTS games (
  email      TEXT PRIMARY KEY,
  state      TEXT NOT NULL,      -- GameState 的 JSON
  best       INTEGER NOT NULL,   -- 歷史最高分,開新局不歸零
  updated_at INTEGER NOT NULL
);
```

`best` 獨立成欄位而不是埋在 JSON 裡，是為了榜單能 `ORDER BY best DESC`；
埋在 JSON 裡就得把所有人的 state 全撈出來在 JS 裡排序。

方法三個：

- `getGame(email)`
- `saveGame(email, state, best)` —— `best` 取 `MAX(舊, 新)`，**由 DO 決定
  而非 client**
- `leaderboard()`

## API

| 端點 | 用途 |
| --- | --- |
| `GET /api/play` | 自己的 `{ state, best }`；沒玩過回 `{ state: null, best: 0 }` |
| `PUT /api/play/state` | 存整份 `GameState` |
| `GET /api/play/leaderboard` | 全員最高分 |

開新局不需要獨立端點 —— 前端呼叫 `newGame()` 後照常 `PUT` 就是了。

### 榜單的接縫

DO 只認得 email，顯示名稱與頭像在 D1 的 `users`。所以 `leaderboard()` 回
`[{ email, best, at }]`，**由 Worker 路由拿這串 email 去 D1 join** 出
`name` / `avatar` 再回給前端。DO 不碰 D1，維持它只管自己 SQLite 的單純性。

### 驗證的立場：不防作弊，只防資料汙染

`PUT` 會檢查 board 是長度 16 的陣列、每格是 `null` 或 2 的次方且
≤ 131072、score 是非負整數且有上限。目的是讓一個壞掉的 client 或手滑的
`curl` 不會把 DO 塞進無法解析的狀態。

要真的防作弊，得在 server 重放整局移動。對 20 個熟人的休息遊戲那是過度
設計。榜單上出現一個離譜分數，社交壓力自會處理。

### 寫入量

debounce 壓到每人每秒最多一次，一局約幾百次寫入，每筆 ~200 bytes。

## UI

原版那套暖橘漸層跟本站的 ink/cream 是兩種語言，不直接搬。

- 磚塊用**單一色相的明度階梯** —— 低數字接近 cream 底，數字愈大愈往 ink
  走，2048 那格用專案既有的 accent 收尾。不必發明九種顏色，也天然保住
  數字的對比度。
- 棋盤固定正方形、`max-width` 約 420px 置中，手機上撐滿寬度。
- 方向鍵要 `preventDefault`，否則頁面會跟著捲。
- 滑動判定門檻 ~30px，避免把點擊誤判成移動。

## 三個必須注意的既有整合點

1. **`/api/play` 絕對不能加進 `frontend/src/lib/sw-guards.ts` 的
   `CACHEABLE_API`。** 那是使用者可變狀態，被 SW 快取住的話玩家會看到一個
   永遠停在舊局的棋盤。跟 `/api/me`、通知、聊天同一類。
2. **要加 e2e fixture。** 新路由沒 fixture 會拿到 `{}` ——
   `frontend/e2e/fixtures/api_play.json` 給一個含棋盤的狀態。
3. **`pnpm test:webkit` 要涵蓋 `/play`。** 這頁有 `useReducer` + 鍵盤/觸控
   事件監聽 + debounce timer 三種生命週期，正是當初 iOS 白屏那類問題的
   溫床。斷言照既有標準：有渲染、沒有 uncaught `pageerror`。

## 測試

`frontend/src/lib/game2048.test.ts`，注入固定序列 rng：

- 合併規則 —— `[2, 2, 4, null]` 左移 → `[4, 4, null, null]`
- 一次移動中已合併的磚不再參與合併
- 移動後才落新磚，且只落在空格
- 沒有合法移動時 `isGameOver` 為真；棋盤滿但仍有相鄰同值時為假
- 分數累加等於本次所有合併結果之和

## 明確不做

undo、動畫特效、每日挑戰、離線遊玩、跟題庫的任何連動、即時對戰。
